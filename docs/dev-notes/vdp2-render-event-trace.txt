VDP2 ordered render-event trace
===============================

The VDP2 memory-write bundle can include `vdp2-render-event-trace.csv`. The
existing `vdp2-memory-write-trace.csv` format remains unchanged. The event file
uses these columns:

    sequence,event,vdp1_frame,row,memory,address,width,value

`event=write` records a committed VRAM or CRAM write that passed the configured
memory and frame filters. `event=scanline` marks the point immediately before
Ymir asks its renderer to render that VDP2 row. Both event kinds share one
monotonically increasing sequence generated on the emulation thread. A write
whose sequence precedes a scanline marker is visible to that row's renderer;
a write with a later sequence happened after that row render began. The
sequence can have gaps because filtered writes still advance it.

`vdp2-vram-start.bin` and `vdp2-cram-start.bin` are snapshots taken when the
tracer is attached and refreshed after a save state loads. The write/event ring
is cleared at the same time, so replay starts from the loaded state's actual
VDP2 memory. Starting from those files, replay the included writes in sequence
order to recover the memory contents at each scanline marker. The export-time
`vdp2-vram.bin` and `vdp2-cram.bin` remain useful as end-state checks. A
complete row-state history requires both start snapshots, a complete event
CSV, and `trace_dropped_total=0` in the bundle manifest. The manifest's
`row_state_reconstruction_complete` flag is stricter: it is true only when the
full VRAM/CRAM address range is enabled and no frame-range filter omits earlier
writes. Narrowly filtered captures can still order the writes they contain,
but cannot claim complete memory state.

This describes the synchronous software renderer, where the row is rendered
inside the call immediately following the marker. Hardware renderers may defer
their work and are not covered by this ordering guarantee. This is a row-render
boundary, not an HCNT or per-pixel bus timestamp. Ymir's
HCNT readback is latched and its current implementation still has a TODO for
deriving HCNT from the global cycle counter. The trace therefore supports
whole-row memory-state reconstruction, but makes no claim about mid-scanline
changes or individual pixel fetch timing. Pair it with the bounded pixel-fetch
trace when investigating source addresses and layer output.

The ring capacity and dropped-row count cover both writes and scanline markers.
For compatibility, `trace_rows` in the receipt remains the number of rows in
the legacy memory-write CSV; `render_event_rows` counts both writes and
scanline markers. An incomplete bundle or nonzero dropped count cannot
establish a complete row-by-row state history. Frame indices use the same VDP1
frame convention as the existing memory-write trace.
